# Spec Delta

## Purpose

Define what a MORPHEUS release discloses about the third-party components it redistributes: the attribution carried
inside each distributed artifact, the inventory published beside them, and how both are kept equal to what is shipped.

## ADDED Requirements

### Requirement: Every distributed artifact SHALL carry the product licence and the third-party notices

The Linux archive, the Windows archive and the payload installed by the Windows installer MUST each contain, at the root
of the application image, the product `LICENSE` and a `THIRD-PARTY-NOTICES` file, and the packaging MUST fail when either
is missing or empty.

#### Scenario: The Linux archive holds both files

- **WHEN** `distribution/build-portable.sh` completes
- **THEN** the application image root contains a non-empty `LICENSE` identical to the repository's and a non-empty
  `THIRD-PARTY-NOTICES`, and the packaging proof prints a `PASS` line for them

#### Scenario: The Windows archive and the installed tree hold both files

- **WHEN** `distribution/build-portable.ps1` and `distribution/build-installer.ps1` complete and the installer is run in
  its smoke mode
- **THEN** the ZIP and the installed directory each contain both files at the image root

#### Scenario: A build that drops a file is refused

- **WHEN** the step that places `THIRD-PARTY-NOTICES` is removed from a packaging script
- **THEN** that script fails before archiving, with a message naming the missing file

### Requirement: The notices SHALL cover exactly the third-party components of the distributed program

`THIRD-PARTY-NOTICES` MUST name every third-party component on the runtime classpath of the distributed module, with its
coordinates, version and licence identifier, MUST reproduce for each the licence text and any notice its licence
requires, and its population MUST be derived by the build rather than listed by hand.

#### Scenario: Every shipped component is attributed

- **WHEN** the packaging runs on a checkout whose distributed module resolves `n` third-party runtime components
- **THEN** the notices hold `n` entries, each with coordinates, version, licence identifier and a non-empty text

#### Scenario: A new dependency without a text fails the packaging

- **WHEN** a third-party dependency is added to the distributed module, its JAR carries no licence file, and no text is
  committed for its coordinates
- **THEN** the packaging fails with `THIRD_PARTY_NOTICE_MISSING` and names the component

#### Scenario: A component that is not shipped is not attributed

- **WHEN** a module of the reactor that is not embedded in the distributed program declares a third-party dependency of
  its own
- **THEN** the notices do not list it

#### Scenario: A version bump needs no edit

- **WHEN** the version of an attributed component changes and its licence does not
- **THEN** the packaging succeeds and the notices state the new version

#### Scenario: A removed dependency leaves no stale entry

- **WHEN** a third-party dependency is removed from the distributed module
- **THEN** the notices no longer list it, and a committed text that no shipped component uses is reported by the
  packaging

### Requirement: The artifact SHALL keep the legal notices of its embedded runtime and name the runtime's origin

The packaging proof MUST require the embedded runtime's legal notices to be present for each packaged runtime module,
and `THIRD-PARTY-NOTICES` MUST name the distribution and version of the JDK the runtime was built from, read from the
build.

#### Scenario: The runtime's notices are present

- **WHEN** the application image is built on either platform
- **THEN** the runtime holds a non-empty `legal` directory for `java.base` and for each module the image adds, and the
  packaging proof says so

#### Scenario: A stripped runtime is refused

- **WHEN** a `jlink` option that removes the legal notices is added to the packaging
- **THEN** the packaging fails and names the runtime module without notices

#### Scenario: The notices name the JDK that was used

- **WHEN** the image is built with a given JDK distribution and version
- **THEN** `THIRD-PARTY-NOTICES` states that distribution and version, and they equal what the embedded runtime's
  `release` file declares

### Requirement: A release SHALL publish the inventory of the tagged commit, with its checksum and provenance

A published release MUST include one CycloneDX SBOM generated by the release build from the tagged commit, a SHA-256
checksum beside it, an entry for it in a release manifest, and a provenance attestation that covers it.

#### Scenario: The SBOM is among the published assets

- **WHEN** the release workflow publishes version `X.Y.Z`
- **THEN** the release holds `morpheus-X.Y.Z-sbom.cdx.json` and `morpheus-X.Y.Z-sbom.cdx.json.sha256`, the checksum
  matches, and a release manifest lists the SBOM with its size and digest

#### Scenario: The SBOM describes the tagged commit

- **WHEN** the qualification reads the published SBOM
- **THEN** its metadata names the product at version `X.Y.Z`, and every third-party component attributed in the archives
  is a component of the SBOM

#### Scenario: The SBOM's provenance verifies publicly

- **WHEN** `gh attestation verify` is run on the published SBOM
- **THEN** it succeeds for the repository, as it does for the three distributed artifacts

#### Scenario: A release without the SBOM does not publish

- **WHEN** the SBOM or its checksum is absent from the downloaded assets in the publish job
- **THEN** the job fails with "Missing release asset" before `gh release create`

### Requirement: The expected asset set SHALL be the same in the release workflow and in both qualification scripts

The list of assets the release workflow requires before publishing and the lists `scripts/verify-release-provenance.sh`
and `.ps1` accept MUST name the same assets, and the build MUST fail when they differ.

#### Scenario: The three lists agree

- **WHEN** the release contract test extracts the asset names from the workflow and from each script
- **THEN** it finds three non-empty lists with the same names, the SBOM and its checksum among them

#### Scenario: An asset added to one list only fails the build

- **WHEN** an asset name is added to `release.yml` and to neither script, or to one script only
- **THEN** the test fails and names the asset and the file that lacks it

#### Scenario: The qualification still refuses anything else

- **WHEN** a release carries an asset that is not in the list
- **THEN** both qualification scripts fail with "release publishes unexpected assets"
