# Design

## Context

- The Windows chain, as read on `8b26d3d7`: `build-release.ps1` requires a clean tagged head, calls
  `build-portable.ps1` (Maven package, `jpackage --type app-image`, packaging proofs, `morpheus-<version>-windows-x64.zip`),
  checksums the ZIP, calls `build-installer.ps1 -SkipPortable` (re-zips the image as `morpheus-payload.zip`, resolves a
  trusted compiler through `ensure-inno-setup.ps1`, runs it on `MORPHEUS.iss`, checksums the installer), then writes
  the release manifest. `release.yml` runs that script in the `windows-release` job after replaying
  `validate-m28.ps1`, then attests the ZIP and the installer and uploads them.
- The installer carries the payload as a ZIP and three scripts; its `[Files]` section copies nothing to `{app}`. The
  uninstaller is generated by the compiler and deployed at install time.
- `validate-m28.ps1` builds the installer, and a second "smoke" installer with its own `AppId`, on every pull request
  and before every release build. `validate-m20.ps1` rehearses `build-release.ps1` nightly on a local tag, with
  `contents: read`.
- `release.yml` has no secret and no `environment:` today; its two build jobs hold `id-token: write` for the
  attestation. `AuditHardeningWorkflowContractTest` pins its trigger and its publication rules.
- `.claude/rules/security.md`: no secret as a CLI flag or a literal; a secret given on a command line is readable by
  other accounts; actions pinned by 40-character SHA; secrets reserved to trusted events.
- External facts read on 2026-10-13. Each is quoted from the source named; where sources disagree it is said. Nothing
  below is asserted from memory, and prices and country lists are perishable — re-read before deciding.
  - *Key custody.* "As of June 2023, the CA/Browser Forum requires private keys for OV certificates to be stored on a
    hardware security module (HSM) or hardware token." — Microsoft Learn, *Code signing options for Windows app
    developers* (`learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options`, dated 2026-08-29).
    The CA/Browser Forum's requirements page (`cabforum.org/working-groups/code-signing/requirements/`) lists the
    ballot (CSC-17); the clause text itself was not read.
  - *Certificate lifetime.* Ballot CSC-31 limits a publicly trusted code-signing certificate to 460 days for
    certificates issued from 1 March 2026. Read in the ballot list of the same CA/Browser Forum page and in secondary
    sources (`sslinsights.com/code-signing-certificate-validity-reduced-460-days/`); one authority announces an
    earlier cut-off of its own (`support.globalsign.com`, "Maximum Certificate Validity"). Not read in the Baseline
    Requirements text.
  - *EV versus OV.* EV "previously bypassed SmartScreen entirely on first download … That behavior was removed in
    2024"; "Paying the EV premium … solely to avoid SmartScreen warnings is no longer justified." — same Microsoft
    page.
  - *Managed signing service.* Azure Artifact Signing (formerly Trusted Signing): "No hardware token required",
    "integrates directly with CI/CD pipelines", "does not provide instant SmartScreen trust". Eligibility for a
    publicly trusted identity: "Individual developers must be located in the United States or Canada"; for
    organizations the two Microsoft pages give **different lists** — USA, Canada, EU, UK on the page above; a longer
    list on the service's quickstart (`learn.microsoft.com/en-us/azure/artifact-signing/quickstart`, updated
    2026-10-08), which also states that identity validation "takes from 1 to 20 business days" and can be completed
    only in the portal, and that a "Public Trust Test" certificate profile type exists (its behaviour was not read).
  - *Open-source programme.* SignPath Foundation offers signing "for qualifying open-source projects" (same Microsoft
    page). Whether MORPHEUS's licence qualifies was not checked.
  - *Inno Setup.* The `SignTool` directive signs "Setup", "the uninstaller, if SignedUninstaller is set to yes" and
    "original source files, if the [Files] section's sign or signonce flag is used"; the tool must be defined in the
    IDE or on the compiler's command line, "otherwise an error will occur" — `jrsoftware.org/ishelp/topic_setup_signtool.htm`.
    That page documents the current release; the repository pins 7.0.2 and task 2.2 confirms the option on it.
  - *GitHub environments.* "Secrets stored in an environment are only available to workflow jobs that reference the
    environment"; a job cannot read them before a required reviewer approves; deployment can be restricted to selected
    branches and tags. Required reviewers are available on public repositories for Free, Pro and Team plans; on
    private repositories, environment features depend on the plan —
    `docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments`.

## Goals / Non-Goals

**Goals**: every Windows binary MORPHEUS produces in a release is signed by one declared publisher and timestamped;
the credential cannot reach a pull request, a command line or a log; the signing path is exercised every night without
the credential; the day the certificate exists, the cutover is one reviewed change and one release.

**Non-Goals**: choosing the provider (maintainer, section 1 of `tasks.md`); re-signing the embedded Java runtime's
binaries; signing the PowerShell scripts the installer runs (they are launched with an explicit execution policy by
the installer; see open questions); signing the Linux archive; re-publishing or re-signing `v1.2.0` and earlier —
published releases are immutable; removing the SmartScreen prompt (no certificate type guarantees it for a new file);
verifying a signature at install or update time.

## Decisions

1. **The launcher is signed in the packaging script, before anything derived from the image exists.** Between
   `jpackage` and the packaging proofs of `build-portable.ps1`. The portable ZIP, the installer payload, both
   checksums, the manifest and the attestation then all describe the signed bytes, and the launcher the installer
   deploys is the launcher the ZIP carries. *Rejected*: signing after the build in a separate workflow job — the ZIP,
   its checksum, the payload and the manifest would have to be rebuilt outside the build scripts, so the rehearsal
   would stop exercising the code that makes a release. *Rejected*: the compiler's `sign` flag on `[Files]` — the
   launcher is not a `[Files]` source, it is inside a ZIP.

2. **The installer and the uninstaller are signed by the compiler, through its signing directive.** The compiler is
   the only actor that can sign the uninstaller it generates. The directive is compiled in only when the build signs
   (a preprocessor branch, as `SmokeMode` already is), so an unsigned build needs no dummy tool.

3. **One signing entry point, which never receives a secret as an argument.** A script under `distribution/windows/`
   takes a file path and nothing else; `build-portable.ps1` calls it for the launcher and the compiler calls it for
   the installer and uninstaller. The provider-specific part — which tool, which endpoint, which timestamp authority —
   is behind it and reads its credential from the process environment or from an already-established federated
   session. The command the compiler is given therefore contains a script path and a file placeholder, and a process
   listing or a build log shows nothing else. *Rejected*: passing a password, PIN or client secret in the compiler's
   tool definition — it is an argument, which `rules/security.md` forbids for the reason it gives for the TLS
   password.

4. **Three declared states, chosen by the caller, printed by the build.** `none`: nothing is signed and the manifest
   says `unsigned`. `test`: an identity generated for this run. `release`: the declared publisher's identity. There is
   no automatic choice: a build does not sign because a credential happens to be present, and does not skip signing
   because one is absent. A build asked for `test` or `release` that cannot sign every expected file fails. A release
   build of a version at or above the signing baseline refuses `none` and `test` — the baseline of the other change is
   what turns "signed" from a capability into an obligation. *Rejected*: "sign when the secret is set" — the absence
   of a secret (a rotated credential, a fork, a mistyped name) would silently publish an unsigned release, the exact
   degradation `rules/code-style.md` forbids.

5. **The credential is reachable from one place: the release workflow, on a tag, behind a protected environment.**
   The Windows release job references an environment restricted to version tags, with a required reviewer if the plan
   allows; the credential is exposed to the build step only, after the tag-reachability check and the replayed M28
   gate have passed. No workflow with a `pull_request` trigger, and not `nightly.yml`, names that environment or that
   credential; `validate-m28.ps1` and the smoke installer never sign with it. A federated identity (no stored secret
   at all) is preferred where the provider supports it — the job already holds `id-token: write`. This is textual by
   nature (`.yml`), held by `AuditHardeningWorkflowContractTest`: the intent is "these names must not appear in a
   workflow a pull request can reach, and no secret expression appears inside a `run:` block".

6. **Every signature is timestamped, and a timestamp failure fails the build.** With certificates limited to roughly
   fifteen months, an un-timestamped signature has a short life. No retry-then-continue: a release without timestamps
   is refused by the qualification anyway (`AUTHENTICODE_TIMESTAMP_MISSING`), so the build stops first.

7. **The rehearsal signs with an identity that is born and dies in the run.** The Windows leg of `release-rehearsal`
   asks `validate-m20.ps1` for a test-signed build: a self-signed code-signing certificate is created in the run's
   personal certificate store, used through the same entry point and the same order as a release, and removed on
   every exit path. The rehearsal then proves (a) the launcher in the ZIP, the launcher in the payload, the installer
   and — after the lifecycle installation — the uninstaller each carry a signature whose signer is that identity;
   (b) the bytes of the two launchers are identical; (c) the qualification's verification refuses those binaries
   (`AUTHENTICODE_SIGNATURE_NOT_TRUSTED` or `AUTHENTICODE_SIGNER_UNEXPECTED`): a release signed by the wrong key would
   not qualify. It never adds the test certificate to a trust store — the other change's gate refuses that step — so a
   "valid" status is not what it proves; presence, signer and order are. Run by hand, the validator stays unsigned
   unless asked, so that it does not create certificates on a developer's machine uninvited. The lane keeps
   `contents: read` and no secret. *Rejected*: a long-lived test certificate in a repository secret — a secret the
   nightly workflow could read, to prove something an ephemeral key proves as well.

8. **What a rehearsal still does not exercise is said by name**: the release identity, the provider's service, and —
   unless the maintainer decides otherwise (open question) — the timestamp authority.

9. **The cutover is one change.** It declares the publisher's subject and the signing baseline (the version about to
   be released), wires the environment and the credential into `release.yml`, switches the release build to `release`,
   updates the user pages, and is followed by the tag. From that commit a release build of that version cannot be
   unsigned. If signing fails at the tag, nothing is published — the existing "no overwrite, no partial release"
   rules already hold that.

10. **A new ADR.** Who the publisher is, where the key may live, that no key file ever enters the repository or a
    runner's disk as a reusable secret, that signing is an obligation from a declared version and not before, that
    earlier releases stay as published. ADR-0089 announces it; ADR-0105 (no reusable secret at rest, for the product)
    is cited for the same instinct applied to the pipeline. Use the `adr-author` and `live-numbers` procedures; add
    its line to the ADR index.

## Risks / Trade-offs

- **The provider decides more than the price.** A hardware token signs only where it is plugged in: a self-hosted
  runner or the maintainer's machine. The second breaks "built by the workflow from the exact tag, attested there";
  the first adds a machine to trust and maintain. A cloud key or a managed service keeps the present chain. The
  specification is written so that only the entry point's inside and the workflow's credential step change with the
  choice — but a token would reopen decision 5.
- **Eligibility may exclude the cheapest option.** The managed service validates individuals only in two countries
  according to its own documentation; the maintainer's legal form and country decide, not the repository.
- **The name on the certificate is a legal identity**, not the installer's `AppPublisher`. Windows will display the
  former. If they differ, the installer's publisher field should follow — a visible change, to be decided.
- **A signed first release still meets SmartScreen.** Reputation is earned per publisher over time. The user page says
  so (other change); the exit criterion of the sprint is "signed and verified", not "no prompt".
- **A test-signed binary exists on a runner for a few minutes.** It is uploaded nowhere (the lane uploads listings,
  not binaries), is not trusted by any machine, and would be refused by the qualification.
- **The compiler's signing option on the pinned version** is read from documentation of the current release.
  Task 2.2 measures it on 7.0.2 before anything depends on it.
- **Renewal.** A certificate that expires between two releases fails the next release build at the signing step —
  loudly, but on the day of the tag. The rehearsal cannot see it (it holds no release identity). A calendar entry is
  the maintainer's; the risk register carries it.

## Open Questions

Decisions left to the maintainer, each with a recommendation. None blocks sections 2 to 5 of `tasks.md`.

- **Provider and key custody**: managed signing service, certificate from an authority on a cloud HSM, or certificate
  on a hardware token. *Recommendation*: a cloud-held key (managed service if eligible, otherwise an authority's cloud
  HSM), because it is the only family that keeps the release built and attested on a hosted runner from the tag.
- **OV or EV**: *Recommendation*: OV-level validation. Microsoft documents no SmartScreen advantage for EV since 2024.
- **Legal identity on the certificate**: individual or organisation, and the exact subject. It determines eligibility
  and what Windows displays. No recommendation — it is a fact about the maintainer.
- **Timestamp authority**: usually the provider's own. *Recommendation*: the provider's, declared beside the
  publisher, with no fallback authority chosen at run time.
- **Does the rehearsal contact a timestamp authority** with its throwaway certificate? *Recommendation*: no on the
  nightly schedule (an external dependency for a throwaway signature), yes when dispatched by hand before the cutover;
  either way the summary says which.
- **Does 1.2.1 wait for the certificate?** *Recommendation*: no. The baseline mechanism exists so that a corrective
  release is not held by a purchase; 1.2.1 ships unsigned and says so, the first release after the certificate is the
  first signed one.
- **What earlier releases say**: *Recommendation*: nothing is re-signed or re-published. The installation page and the
  release notes of the first signed version state from which version releases are signed; older installers remain
  verifiable by checksum, and `v1.2.0` by nothing more.
- **Sign the installer's PowerShell scripts?** *Recommendation*: not in this change — it changes how the installer
  launches them and is outside the sprint's exit criterion; record it in the ADR as considered.
- **Required reviewer on the signing environment** when the maintainer is the only reviewer and the one who pushes
  the tag: *Recommendation*: restrict the environment to version tags in any case; add the reviewer if the plan and
  the repository's visibility allow it (task 1.5 measures that).
