## 3. The change

- [x] 3.1 The MCP runtime inside a scope. Proof: 2.1 passes; the MCP tool tests pass unmodified.
      *2026-10-13: `MorpheusMcpRuntime` opens a scope, then its seven stores inside it. **One thing the MCP tool tests caught**: opened through a scope, a database that cannot be opened raised `IllegalStateException`, which no tool handler answers, where the first store used to raise `KnowledgeStoreException`. The runtime translates it, and lets the nesting refusal through. All 147 MCP tests pass; the two of `McpStoreFailureInjectionTest` failed before the translation.*
- [x] 3.2 One runtime per adapter; the inner runtime of the query service absorbed; the remaining sites. Proof: 2.2
      passes; `AdapterCompositionRootArchitectureTest` green with a shorter list.
      *2026-10-13: **not done as specified, and deliberately.** One runtime type per adapter would move every named composition root to correct the one site that 1.1 found. The composition tools open a scope; the rule of 2.2 holds the invariant for every class. `AdapterCompositionRootArchitectureTest` is green with the same list: no class stopped reaching a concrete store. The inner runtime of the query service is not absorbed.*
      *2026-10-13, second pass: the inner runtime of `MorpheusQueryApiService` is gone, **absorbed into `SqliteQueryRuntime`, not into `ApiRuntime`** - a departure from the design's "one runtime per adapter", for a reason read in the code: the inner runtime opened the same five stores and wired the same three services as `SqliteQueryRuntime`, which the CLI and the MCP server already shared. It was a third copy of that, and the only one with a scope. The scope moved into `SqliteQueryStores` and `SqlitePolicyStores`, so the policy lives in the module that owns the connection, and HTTP opens the shared runtime like the two others. Still not done: one runtime type per adapter (HTTP has `ApiRuntime` and the two shared runtimes), and `AdapterCompositionRootArchitectureTest` is green with the **same** list, not a shorter one - `MorpheusQueryApiService` still reaches `store-sqlite` through the shared runtime. The box stays open on that proof.*
      *Observable differences, for the reviewer: a database that cannot be opened is reported by the query and policy runtimes as before - `KnowledgeStoreException`, "Cannot initialize SQLite knowledge store", the `SQLException` as cause (`SqliteRuntimeConnectionTest`). Two things did change. The stores of one query or policy operation now read through one connection on the CLI and MCP, and on all three transports for policy: reads that were independent share a view. And such a runtime opened while another scope is open on the thread is now refused (`SQLITE_CONNECTION_SCOPE_NESTED`) where it used to open its own connections; no call site does that, and the 150 MCP, 403 API and 1741 CLI tests pass.*
      *2026-10-15, third pass: **done.** One class builds the stores of an operation, `SqliteOperationRuntime` (`morpheus-store-sqlite`): it always opens the scope first, builds each store the first time the operation asks for it, registers it for release at once, and wires the query and policy services. `SqliteQueryRuntime`, `SqlitePolicyRuntime`, `SqliteQueryStores`, `SqlitePolicyStores` and `SqliteStoreConnection.openScope` are deleted. Each transport has one runtime type wrapping it - `ApiRuntime`, `CliRuntime`, `MorpheusMcpRuntime` - whose accessors answer application ports, so a service reading through it depends on no SQLite type. Proof: `AdapterCompositionRootArchitectureTest` green with `COMPOSITION_ROOTS` at **5, from 32** (`ApiRuntime`, `MorpheusMcpRuntime`, `MorpheusProjectSyncApiService`, `MorpheusRemoteHttpServer`, `MorpheusRemoteHttpServerBootstrap`); classes of the four modules that build a store **16 to 3**, scope openings **7 to 1**, single-store classes outside a scope **10 to 2**, each named with its reason (`SqliteServerMaintenance`, `CliProjectWriteCapabilityResolver` - called from inside another runtime's operation, where opening a runtime would nest).*
      *Rules strengthened (2.2): the textual rule reads code without comments, requires the opening before the first construction, and holds two closed lists instead of "at least six"; the bytecode rule requires a **call** to `SqliteConnectionScope.open` from any class that builds **one** store, where it asked for a dependency on the scope from a class that builds two. Broken with three scratch classes (opening in a comment, opening after the store, scope taken as a parameter): the text refused all three, the bytecode the first and third - it cannot see order. Reverted.*
      *Observable differences: a database that cannot be opened is `KnowledgeStoreException` on all three transports (HTTP and CLI raised the scope's `IllegalStateException`; MCP had a message of its own); a store is built after the runtime opens, so a schema written by a newer MORPHEUS fails at the first store asked for, not at opening - every site opens the runtime in the `try` that uses it. The CLI keeps the recovery of interrupted publications on the commands that did it (`CliRuntime.recovering`) and not on query, policy and portfolio (`CliRuntime.open`). ADR-0109, third amendment.*
